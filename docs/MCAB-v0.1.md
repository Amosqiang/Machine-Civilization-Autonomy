# MCAB v0.1 — 数据与评分规范（草案）

本规范使现有本体、1000维表与证据记录能够被一致填写和校验。v0.1 仍处于框架完善阶段；这里定义的是数据约定和评估纪律，不表示100个子系统已完成专家审定，也不表示2026基线已有实证评分。

研究原则见 [RESEARCH_PROTOCOL.md](RESEARCH_PROTOCOL.md)，后续阶段见 [ROADMAP.md](ROADMAP.md)。每份报告必须明确证据截止日。原计划的2026基线截止日为2026-10-31；按照本次“当前最新”研究要求，2026最新对照报告改用 **2026-11-02**（Asia/Shanghai）。晚于某份报告截止日的材料不能回填成该版当时已知的事实；更新版应保留自己的核验日期。

## 1. 研究边界与观察条件

评估对象是指定边界内的机器技术—工业系统，而不是脱离能源、硬件和供应链的模型能力。每次实证评估应在证据记录的 `observed_capability`、`upstream_dependencies` 和 `notes` 中说明：

- 系统、设备或软件版本，任务及成功条件；
- 观察起止时间或持续时长，运行负荷及故障范围；
- 保留和移除的人类操作、维护、决策及外部服务；
- 初始设施、预装知识、备件、原料和能源库存；
- 实测结果与推断的边界，以及未观察到的长期行为。

库存耗尽前的无人运行可以支持有时间边界的能力判断；它本身不能证明关键输入可持续供应。初始化、远程接管、人工补给和上游人类生产都必须披露。局部系统无人在场，也不能自动证明整个工业链达到闭环。

## 2. 本体、标识符与文件职责

| 文件 | 内容与约定 |
| --- | --- |
| `data/taxonomy.csv` | 10个领域，每个领域10个子系统，共100行。字段：`domain_id,domain,subsystem_id,subsystem,definition,criticality`。 |
| `data/metrics.csv` | 10个统一指标。字段：`metric_id,metric,definition`。 |
| `data/dimensions.csv` | 由本体与指标生成的1000行HR0评估工作表；不是已完成评分的数据集。 |
| `data/evidence_schema.csv` | 证据记录的字段字典，字段为 `field,description`；它不是证据记录本身。 |
| 单独保存的证据CSV | 按字段字典记录具体来源、HR场景、能力和边界，可交给校验器检查。 |

`domain_id` 使用字符串 `1` 至 `10`。`subsystem_id` 使用 `<domain_id>.<子系统序号>`，子系统序号为1至10，例如 `1.1`、`1.10`。这些是标识符，不能按小数处理。`metric_id` 为 `M1` 至 `M10`；`dimension_id` 为 `<subsystem_id>-<metric_id>`，例如 `1.10-M10`。

1000维来自 **100个子系统 × 10个指标**，每个组合恰好出现一次。阅读和生成时应保持自然指标次序 `M1,M2,…,M10`，避免将 `M10` 排在 `M2` 前。本体中的名称、定义和领域归属必须一致；更改既有标识符需要说明版本及迁移关系。

`criticality` 使用当前本体的 `high` 或 `critical`。它是本体中的研究判断，不是经过验证的依赖边，也不能单独证明某个节点不可替代。

## 3. HR场景与1000维表的关系

| 场景 | 人类参与条件 |
| --- | --- |
| HR100 | 人类参与的现实基线。 |
| HR50 | 在明确分母的条件下，保留约50%的人类参与。 |
| HR10 | 保留约10%的人类参与，说明仍保留的关键岗位。 |
| HR1 | 保留极少数人类岗位，逐项说明最后的人类参与。 |
| HR0 | 在声明的系统边界与观察时段内，无新增人类参与。 |

HR50、HR10和HR1并不是可直接互换的精确实验设置。研究者必须说明比例按劳动小时、岗位、决策权限还是其他量计算；缺少分母的来源只能作有边界的描述，不能与另一设置直接比较。不能从HR100线性插值出其他场景结果。

`dimensions.csv` 的问题统一指向 **HR0**，仅保留每个维度当前的HR0评分及证据摘要。五种场景的明细记录在证据CSV中，以 `human_removal_scenario` 区分。1000维是维度数量；完整五场景评估涉及5000个维度—场景组合，并可包含更多来源记录。生成1000行空表不意味着这些组合已获验证。

## 4. 评分、证据与置信度

### 4.1 自主性分数

`score_0_5` 填整数0至5，沿用现有自主等级：

| 分数 / 等级 | 判定锚点 |
| --- | --- |
| 0 / H5 | 该项关键能力必须依赖人类。 |
| 1 / H4 | 能自动执行正常任务，但异常处理或维护依赖人类。 |
| 2 / H3 | 具备局部自治，可处理部分故障或情形，仍有关键外部依赖。 |
| 3 / H2 | 在声明范围内，多数相关维护、输入或扩容环节可自主完成。 |
| 4 / H1 | 该项能力接近独立，仍有少量关键人类供应或操作依赖。 |
| 5 / H0 | 在声明范围和足够支持该项主张的观察期内，该项能力达到宿主独立。 |

这些锚点须结合 `metrics.csv` 中对应指标解释。例如，M1评估无人完成正常任务的能力，M4评估修复与重新投运，M10评估建立同等功能的新系统。M1的高分不会自动赋给M4或M10，也不要求把全部十项能力重复塞进每个指标。记录必须说明该分数的判定依据及边界；当前草案尚未为每个子系统制定完整的指标专属量化阈值。

**空值表示未知或尚未评估；0分表示有依据判断为完全依赖人类。** 不得用0分填补缺少证据的维度，也不得把序数分数当作百分比或测量出的工业闭环率。

### 4.2 证据等级

| 等级 | 证据范围 |
| --- | --- |
| E5 | 现实长期无人生产运行数据。 |
| E4 | 现实短期无人实验或工业现场验证。 |
| E3 | 高保真试验场或原型系统。 |
| E2 | 实验室演示。 |
| E1 | 仿真、模型或厂商声明。 |
| E0 | 无直接证据，仅有推断。 |

在1000维表中，`evidence_type` 填上述 **E0—E5**；在证据记录中，对应字段叫 `evidence_level`。来源类型另用证据记录的 `source_type` 表示，不能填入 `evidence_type`。证据等级描述验证方式，不等于自主性分数。

E0推断必须有可追溯的推断依据，并在 `notes` 明确标记其为推断；若没有足以评分的依据，分数应留空。模型宣传、演示视频或单一厂商声明不能单独支撑正式自主性评分。多个来源存在冲突时，应记录冲突和适用条件，不能只选最高能力主张。

### 4.3 两种置信度字段

`dimensions.csv` 的 `confidence_0_1` 接受0至1的有限数值，表示分析者对该项评分可靠性的判断；它不是已校准的统计概率。填写者应在 `notes` 解释关键不确定性。

证据记录的 `confidence` 使用现有类别：`High`（多来源一致的现实运行证据）、`Medium`（单一高质量来源或局部现实证据）、`Low`（实验室、仿真、推断或信息不足）。两种字段服务于不同粒度，**当前版本没有数值与类别之间的自动换算规则**。

## 5. 1000维表字段

| 字段 | 含义与填写规则 |
| --- | --- |
| `dimension_id` | 子系统与指标的唯一组合ID。 |
| `domain_id`、`domain` | 从本体复制的领域ID与名称。 |
| `subsystem_id`、`subsystem` | 从本体复制的子系统ID与名称。 |
| `metric_id`、`metric` | 从指标表复制的指标ID与名称。 |
| `test_question` | 该子系统在HR0条件下是否具备该指标能力。 |
| `criticality` | 从本体复制的重要性判断。 |
| `score_0_5` | 0—5整数；未知留空。 |
| `confidence_0_1` | 0—1有限数值；评分后必填。 |
| `evidence_date` | 评分所用证据的核验截止日期，格式 `YYYY-MM-DD`；评分后必填。 |
| `evidence_type` | E0—E5；评分后必填。 |
| `source` | 可追溯来源或所依据的证据记录引用；评分后必填。 |
| `notes` | 评分理由、边界、不确定性；使用E0评分时必须明确说明推断。 |

来源有多条时，应把逐条细节放入证据CSV，再在工作表中引用。生成器产生的初始评分和证据字段均为空，不包含任何实证结论。尚未评分的行可以先填写部分证据元数据；已填写的数值、日期和等级仍须有效。E0行的 `source` 可以引用解释推断依据的证据记录，不应为了满足必填要求编造直接证据。

## 6. 证据记录字段

证据CSV使用 `data/evidence_schema.csv` 中现有的23个字段，不额外创建隐含的列。一个记录对应一个子系统、指标和HR场景下的一条来源及分析；多条来源应保留各自的 `record_id`。

| 字段 | 约定 |
| --- | --- |
| `record_id` | 在证据文件中唯一的非空记录ID。 |
| `year` | 所属基线年份，例如2026。 |
| `as_of_date` | 此记录采用证据的截止日期，`YYYY-MM-DD`。 |
| `domain_id`、`subsystem_id`、`metric_id` | 引用本体和指标表中的有效ID，领域必须与子系统一致。 |
| `human_removal_scenario` | HR100、HR50、HR10、HR1或HR0。 |
| `score_0_5` | 该记录所支持的0—5整数评分；不支持评分时留空。 |
| `evidence_level` | E0—E5。 |
| `confidence` | Low、Medium或High。 |
| `observed_capability` | 来源实际支持的能力、实验条件及时间范围。 |
| `remaining_human_role` | 仍然必要的人类操作、技能或供应。 |
| `failure_mode` | 已观察或明确声明的失败和边界条件。 |
| `upstream_dependencies` | 所需上游能力、设备、材料、能源或服务。 |
| `substitutes` | 可替代路径及其验证范围；未知应明确说明。 |
| `recovery_time` | 恢复时长，包含单位、条件及实测或估计属性。 |
| `stockpile_duration` | 无补给可维持时长，包含单位与库存假设。 |
| `single_point_of_failure` | Yes、No或Unknown；No需要相应替代或冗余依据。 |
| `source_title`、`source_url` | 可追溯的来源标题和网址。 |
| `source_type` | Paper、benchmark、field-data、company-doc、government或other。 |
| `source_date` | 来源发表或观察日期，`YYYY-MM-DD`；不能晚于 `as_of_date`。 |
| `notes` | 分母、推断、冲突来源、评分理由及其他未结构化边界。 |

每条记录必填 `record_id,year,as_of_date,domain_id,subsystem_id,metric_id,human_removal_scenario,evidence_level,confidence,observed_capability`。E1—E5还必填四个来源字段 `source_title,source_url,source_type,source_date`。E0没有直接证据，可以不填这些来源字段，但必须填写 `notes` 说明推断及依据；不能省略必填的记录身份和分析内容。`year` 为四位基线年份，`as_of_date` 不能晚于该年份；还应遵守具体报告声明的截止日。

2026最新对照研究另存于 `data/research/2026/domains_*.json`，保留逐维度的目标能力、已核验能力、证据适用关系、差距和验证需求，并由 `scripts/build_2026_report.py` 生成报告。该对照资料不等同于上述五场景评分记录，不自动回填0—5分，也不把当前访问到的厂商文档视为已完成HR0验证。未能核实发布日期的当前文档应留空发布日期，同时保留核验日期与局限。

尚未获得的信息应保留未知，不要制造恢复时间、库存量或依赖关系。`single_point_of_failure` 尚未分析时也可留空。校验器检查列集合、ID、必填项和已实现的值约束，不检查来源网址的实际内容，也不自动判断其是否支持所填主张。观察是否足够长期、推断是否合理及是否遵守特定版次的研究截止日，仍需要人工研究与复核。

## 7. 关键路径与四个总指标

关键路径分析至少记录上游依赖、替代路径、恢复时间、库存时长、单点故障与最后不可替代的人类角色。应区分“本体标为critical”与“证据确认不可替代”。未经验证的推定依赖应明确标注，不能冒充实证依赖图。

四个总指标继续沿用概念定义：C表示工业闭环度，H表示移除人类后的性能损失，R_M表示生命周期内建立同等能力后代系统的平均数量，g₀表示HR0下的长期净增长率。本版本**不规定可从1000维分数直接计算这些物理量的公式**。工程层的`mcab-proxy-v0.1`仅提供明示的序数筛查约定，定义和完整性门槛见[开发说明](DEVELOPMENT.md)；C_proxy/H_proxy不等于实测C/H。简单平均、将最低序数分数归一化、或用演示次数替代复制数，均不能得出这些量。

估计总指标需要先声明系统边界、时间跨度、输入产出或资本口径、依赖与替代结构，以及不确定性。条件不足时应报告未知和缺失证据，而不是给出一个看似精确的总分。观察期内依靠库存维持，与可持续闭环和长期增长必须分别报告。

## 8. 生成、校验与修改工作流

项目脚本仅需Python标准库。从仓库根目录运行：

```sh
python3 scripts/validate_data.py
python3 scripts/generate_dimensions.py
python3 scripts/validate_data.py --require-dimensions
```

生成器默认写入 `data/dimensions.csv`。它应先检查输入，再生成1000个唯一组合；目标已存在时拒绝覆盖，以保护人工填写的分数与证据。确认已有文件可以丢弃并完成备份后，才使用显式覆盖：

```sh
python3 scripts/generate_dimensions.py --force
```

`--force` 会重建空白工作表，清除目标文件已有评分与证据，不负责迁移人工数据。

默认校验本体和指标，并在 `dimensions.csv` 存在时一并校验；没有生成表时不把它当作失败。`--require-dimensions` 要求生成表存在。按同一规范校验证据CSV：

```sh
python3 scripts/validate_data.py --evidence path/to/evidence.csv
```

校验通过说明结构及已实现的数据约束通过，不表示评分获得专家认可，也不表示完成全部研究规范。修改本体、字段或脚本行为时，应检查旧数据兼容性，运行相关验证，并说明影响；不要为了让校验通过而删除未完成或存在争议的研究记录。
